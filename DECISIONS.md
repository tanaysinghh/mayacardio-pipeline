# Decisions and interpretations

Each entry: the ambiguity, the choice made, and why. Deviations from the build brief are marked **Deviation**.

## Build and tooling

- **D1. Java version.** Source/target release 17 (runs on Raspberry Pi OS `openjdk-17-jre-headless`); developed and tested on JDK 21.
- **D2. Spring Boot 4.1.1** for the cloud module (current stable at time of writing). Jackson 2 is used directly in `core`; Spring's own Jackson 3 is not used by our controllers (they return pre-serialised JSON), so the two do not interact.
- **D3. Maven wrapper** (`mvnw`, Maven 3.9.16) so a fresh board only needs a JDK.

## Spec documents

- **D4.** `docs/ASSESSMENT_SPEC.md` holds the SPEC section verbatim. The rest of the brief (architecture, stand-in instructions, work order) is saved verbatim in `docs/BUILD_BRIEF.md`.

## Processing logic interpretations (core module)

- **D5. Peak definition is global and sequential.** "At least 100 samples after the previous peak" refers to the previous *peak* (not candidate), which makes peak status depend on history. The reference meaning is a scan from index 0 of the session. `PeakDetector` computes the same set locally: it searches backwards for an index `p` with no candidate in `[p-99, p-1]` (from there the greedy selection cannot depend on anything earlier) and runs the greedy scan from `p`, doubling the lookback when needed, down to the session start. A randomized unit test checks it against a naive global scan, including gaps and dense-candidate signals.
- **D6. "Larger than half of the maximum"** is evaluated exactly in integers as `2*v[i] > max(v[i-800..i-1])` (no floating point).
- **D7. "Available"** means the sample is stored (on the device) or held (in the cloud). Peak conditions require the 800 previous samples, the sample itself and the next sample to be available; a missing sample is never a peak.
- **D8. heart_rate null rule "any sample in those 5 seconds is missing"** is applied to sensor 1 only (heart rate is derived from sensor 1 channel 2). Missing sensor 2 samples do not null the heart rate.
- **D9. Heart-rate arithmetic** follows the spec literally: gaps are converted to seconds (`gap/400.0`), averaged, then `60/mean`. Different but mathematically equal orders can differ in the last floating-point bit; this only matters at exact rounding ties.
- **D10. Rounding** uses round-half-even on the exact binary value of the double (`new BigDecimal(x).setScale(1, HALF_EVEN)`), which is exactly Python's `round(x, 1)` and NumPy's `round`. Means of integer windows of 400 samples hit exact `.x5` ties (for example `.25`, `.75`) about once in 200 values, so the reference's rounding mode matters. If the reference turns out to use half-up, change `Rounding.MODE` in one place. Listed in MANUAL_TODO to verify against the real reference.
- **D11. Means** are `sum/count` with the integer sum computed exactly (long) then divided in double, which equals Python `sum(v)/len(v)`. min/max are integers (no rounding). `magnitude` sums `sqrt(c1^2+c2^2)` in index order.
- **D12. Result JSON shape** (not fixed by the spec): one line per window and mode with `session, window, mode, missing_1, missing_2, complete, mean_1, min_1, max_1, mean_2, min_2, max_2, magnitude, heart_rate` plus timestamps. Per-channel fields are arrays (sensor 1: 3 values, sensor 2: 2 values); the whole array is `null` when the sensor has no available sample in the window.
- **D13. Window readiness.** A window is computed only once every input index is *resolved*: either available or known to be lost (or beyond the end of a closed session). Sensor 1 needs `[400w, 400(w+1)]` (the extra sample is the "sample after" of the last candidate), sensor 2 needs `[400w, 400w+399]`, plus the heart-rate lookback when `w >= 4`. Because resolved inputs never change, a computed result is final; there is no "provisional" result.
- **D14. Batch wire format** between device and cloud is a small binary format (`BatchCodec`): gzip of runs of samples, delta + zig-zag varint per channel. It is several times smaller than JSON, which matters for catch-up time and the network figure.

## Mock stand-in and checker

- **D15. Stand-ins are clearly separate.** `mock-standin` (jar `biosignal-mock-standin.jar`) and `check-standin` (in `pipeline-tools.jar`) are our own implementations of the published protocol, not the official tools. The device code depends only on the wire protocol, never on stand-in classes (the device module has the stand-in as a test-scope dependency only).
- **D16. Ramp channel numbering** is 1-based (`(3i + c) mod 8388608` with `c = 1..3` for sensor 1, `c = 1..2` for sensor 2), matching the spec's "channel 1/2/3" wording.
- **D17. Stand-in behaviour where the spec is silent** (the pipeline does not rely on any of these): a reply with `count: 0` has `first_index` equal to the next index the mock would deliver; a `from_index` read moves the mock's per-sensor cursor; a read older than the buffer reports `buffer_overflow` for the unavailable part; a sensor outage is reported progressively as `sensor_outage` ranges; `session_end` is true once the cursor reaches the end of the session; a stall drops requests without replying; restart creates a new random 8-hex-digit session id and closes the client connection.
- **D18. Stand-in extras for testing only:** `--speed` (simulated clock factor), a localhost control port (`stall`, `corrupt`, `duplicate`, `outage`, `restart`, `status`) and a ground-truth JSON file per session (`generated` count, outages) that `check-standin` uses.
- **D19. check-standin pass criteria:** no duplicates, no wrong values, no sample outside generated range, no silent loss (every index below `generated` is exported or inside a declared loss), no exported index inside a declared loss, no overlapping losses. `check-results` recomputes windows with a separate naive implementation (global peak scan) from an export and compares field by field.

## Device collector and storage

- **D20. Primary key.** The samples table key is `(sid, sensor, idx)` where `sid` is a small integer mapped 1:1 to the mock's `session_id` in the `sessions` table (unique). This is the spec's `(session_id, sensor, idx)` key without repeating the 8-character string in every row (smaller database, fewer bytes written). Table is `WITHOUT ROWID`, so the key is the clustered index.
- **D21. Every read is a `from_index` read.** After the first plain read on each connection (used only to learn the `session_id`), the collector always asks for `from_index = next expected index`. Replies are self-describing (`first_index`, `lost`), so a duplicated or late reply can never shift data to the wrong index; overlap with already-committed data is skipped and the primary key would reject it anyway.
- **D22. Loss ledger tiles the index space.** For each sensor, every index below `next_index` is either stored or inside exactly one recorded loss. Gaps are labelled with the mock's own `lost` reason where it reported one, otherwise `not_delivered_by_mock`. The mock's `lost` hints for indices ahead of us are remembered in memory so a later gap still gets the mock's reason.
- **D23. `session_end`** is honoured only when the reply also has fewer samples than the largest reply seen so far (i.e. we are caught up), so a mock that sets the flag on every post-end reply cannot make us stop early.
- **D24. Session change** (new `session_id` in any reply): flush pending writes, record `[next_index, null]` for each sensor of the old session with reason `mock_session_restarted_unread_tail`, close it, start the new session at index 0. Restart detection does not depend on the TCP connection dropping.
- **D25. Mock stall:** each request has a 2 s reply timeout (monotonic); the same request is re-sent; after 3 consecutive timeouts the TCP connection is closed and re-opened (the mock serves one client at a time).
- **D26. Disk full:** a reserve file (`disk-reserve.bin`, 8 MB) is kept in the data directory. When free space drops below 16 MB or SQLite reports `SQLITE_FULL`, the collector deletes the reserve, keeps reading the mock and buffers replies in memory (up to 48,000 samples per sensor, 2 minutes), and writes only small loss records until free space is back above 48 MB. Beyond the memory cap the oldest buffered samples are dropped and recorded as `disk_full` losses. If the process dies while buffering, the buffered samples are lost and, on restart, show up as the mock's `buffer_overflow` (or `not_delivered_by_mock`) loss, not as `disk_full`.
- **D27. Poll cadence:** each sensor is polled every 500 ms when caught up (so a reply carries about 200 samples, one SQLite transaction with fsync each), and back-to-back while catching up. This sets the power-cut exposure: committed data is durable; data generated since the last commit (normally ≤ 0.5 s, worst case ≈ 1 s under load) is lost on a power cut.

## Cloud service

- **D28. Storage interface.** `CloudStore` is the backend interface; `JdbcCloudStore` implements it for SQLite (embedded, local runs and hosts with a persistent disk) and PostgreSQL (hosted free tiers such as Neon or Supabase), selected with `CLOUD_STORAGE=sqlite|postgres`. A `postgres://user:pass@host/db` URL is accepted as given by providers and converted to JDBC. Both backends pass the same end-to-end test.
- **D29. Cloud storage unit is a 400-sample segment per (session, sensor, window)**, holding a presence bitmap plus delta/varint values, deflated. Idempotency is still per sample: merging a batch sets only absent samples; an already-present sample with the same values counts as a duplicate, a different value counts as a conflict and the original is kept (never overwritten). This keeps one hour of data near 10 MB instead of ~290 MB as one row per sample, which matters for 0.5 GB free database tiers. **Deviation** from the literal "upsert on (session, sensor, idx)": the semantics are the same, the physical key is per segment.
- **D30. Single cloud instance assumed.** Per-session, per-sensor locks are in-process, so the service must run as one instance (true for every free tier considered). Results are written only by that instance.
- **D31. Cloud results are final when written.** A window is computed when all its inputs are resolved (held, or declared lost by the device, or past the end of a closed session); see D13. The cloud stores `mode=online` results with `computed_at`, `data_received_at` (time of the ingest that preceded computation) and `device_captured_at` (device wall clock of the newest batch) for latency analysis. Windows that only become computable after catch-up get a late `computed_at`; they are still `mode=online` (processed in the cloud).
- **D32. Offline results** computed on the device are also uploaded and kept in the cloud with `mode=offline`, so the cloud account holds one line per window and mode.
- **D33. API auth** is a shared bearer token (`CLOUD_API_TOKEN`) on `/api/*`. `/health` is open so the heartbeat stays cheap.

## Streaming, switching, catch-up, commands

- **D34. Two upload lanes.** The live lane sends, every second, everything committed since its last acknowledgement but at most the newest 4,000 samples (10 s) per sensor; the catch-up lane reconciles everything older against the cloud's held ranges (`GET /ranges`), oldest first, in 40,000-index chunks containing both sensors, 2 requests in parallel. After an outage the live lane resumes at "now minus 10 s", so live windows (which need 5 s of heart-rate context) are computable immediately while the backlog drains behind them. Overlap between lanes is harmless (the cloud is idempotent).
- **D35. Mode switching** is driven only by the heartbeat (`GET /health` every 2 s, 1.5 s timeout): offline after 2 consecutive failures, online after 2 consecutive successes; an upload failure triggers an immediate extra heartbeat. Worst case to go offline ≈ 2 + 2 + 1.5 s; to go online ≈ 4 s. On every mode change all in-flight upload requests are aborted (a request sent just before a WiFi drop would otherwise hang until its timeout and delay catch-up).
- **D36. Initial mode** after start is offline until two heartbeats succeed (~2 s). Windows finalized in that interval are processed offline as well; later the cloud processes them too, so a few windows have both an offline and an online line.
- **D37. Offline processing** starts from the first window whose data was not yet acknowledged by the live lane (minus one window of margin) and runs while offline; when the device goes back online it finishes every window that is already computable, then stops. Windows from the offline period get an `online` result too once catch-up delivers their data.
- **D38. `pipeline status` backlog** is `samples_saved - samples_in_cloud` and includes about one second of data in flight during normal streaming; it is never exactly zero while online. Tests treat "≤ 2 s of data and no catch-up backlog" as synced. `samples_in_cloud` for the current session comes from the cloud's acknowledgements (held counts), for older sessions from the last persisted value.
- **D39. Unread tail of an interrupted session** is declared (`to_index: null`) when the device first sees the new session id, not when the mock disappears: a refused or dropped connection cannot be told apart from a short stall that the mock buffer would cover. An export taken while the mock is down therefore does not yet list that tail.
- **D40. `pipeline results`** prints the device's offline lines plus the cloud's online lines (deduplicated by window and mode). If the cloud is unreachable it prints the device lines and says so on stderr.
- **D41. The service does not wait for the network at boot** (`After=local-fs.target` only), so collection starts even when the hospital WiFi is down. It runs as a dedicated `pipeline` user; the `pipeline` wrapper re-runs CLI commands as that user so SQLite's WAL files are never created with the wrong owner.
- **D42. Status file in `/run/pipeline` (tmpfs)** so the 1-second status refresh causes no disk writes; `pipeline status` falls back to reading the database when the daemon is not running. A file lock in the data directory tells the CLI whether the daemon is running (no wall-clock freshness check).
- **D43. Scripts** are POSIX shell/bash with awk only (no Python), keeping the code base Java plus shell.

## Resource tuning, evidence, hosting

- **D44. SQLite page size 1 KB** (set when the database file is created, before WAL is enabled, otherwise SQLite keeps 4 KB). A/B measurement: 573 → 336 MB/h written at the same CPU. Override with `PIPELINE_DB_PAGE_SIZE` (only affects newly created databases).
- **D45. Stored-range index:** the open run of stored indices lives in `stream_state` (already updated by every commit); `stored_runs` gets a row only when a gap closes a run. One fewer page rewritten per commit; tests assert the index always equals the actually stored indices.
- **D46. Accelerated backlog test.** Generating 2 hours of data in real time is impractical here, so the stand-in generates at 20x while the network is cut and returns to 1x when it is restored. Because the stand-in's buffer is defined in samples, it was raised to 200 s of data (10 s of wall time at 20x) for that test only; with the 10 s buffer the device occasionally fell more than 0.5 s of wall time behind at 20x and the stand-in declared `buffer_overflow` (declared, not silent). The catch-up itself (5.76 M samples) is full scale.
- **D47. Latency exclusion rule.** Online-latency statistics exclude windows that ended less than 5 s before a disruption, during it, or within 10 s after recovery: their 5 s deadline overlaps the outage, so no design can meet it. They are counted separately in the evidence.
- **D48. Hosting choice:** Render free web service + Neon free Postgres (both card-free). Hugging Face Docker Spaces now need a paid plan and Koyeb shows no free compute tier; Northflank's sandbox may require a card; Oracle Always Free requires one. See docs/DEPLOY_CLOUD.md.
