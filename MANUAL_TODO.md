# Manual steps (need a human)

Everything here was deliberately not done by the agent: accounts, logins, hardware, video, email. Do them in this order.

1. **Obtain the official `biosignal-mock` and `check_ground_truth`.** Re-run all tests against them: start the official mock on the board (port 7100), run the pipeline for a while, then `pipeline export --session current --from device > dev.jsonl` and run `check_ground_truth` on it. Also re-run the failure scenarios (docs/TESTING.md, "Real-board checklist"). Things to watch, because the stand-in had to guess them (DECISIONS D17, D23): what `first_index` is on an empty reply, whether `lost` is re-reported on `from_index` re-reads, how `session_end` behaves, what happens on a `from_index` beyond the head.
2. **Check the rounding rule against the official reference.** We use Python `round()` semantics (half-even on the exact double; DECISIONS D10). If the reference uses half-up, change `Rounding.MODE` in `core` (one line) and re-run `./mvnw test`.
3. **Create a GitHub repository and push** this repo (it has no remote yet): `git remote add origin <url> && git push -u origin main`. Render deploys from it.
4. **Neon (free, no card):** sign up, create a project (pick a region near your Render region), copy the `postgresql://...` connection string. See docs/DEPLOY_CLOUD.md.
5. **Render (free, no card):** sign up, New → Blueprint → this repo (`render.yaml`), paste the Neon string into `CLOUD_JDBC_URL`, deploy, copy the generated `CLOUD_API_TOKEN`. Check `https://<service>.onrender.com/health`.
6. **Keep the free Render service awake:** create a free uptime monitor (for example UptimeRobot) that calls `https://<service>.onrender.com/health` every 5 minutes. Without it, a device outage longer than 15 minutes lets Render put the service to sleep and the switch back to online takes about a minute instead of under 10 seconds (data is not affected).
7. **Raspberry Pi 4 setup:** flash Raspberry Pi OS 64-bit (Bookworm), connect it to the network, clone the repo, build and install (README "Install and run on a fresh board") with `--cloud-url` and `--token` from step 5. Start the official mock on port 7100 (or `--with-mock-standin` for a dry run).
8. **Real-board failure tests** (docs/TESTING.md checklist): network cut (`ip link set wlan0 down` or unplug), `systemctl kill -s SIGKILL pipeline`, a real **power pull**, disk full with `fallocate`, a clock jump with `date -s` (NTP off). Save outputs of `pipeline status`, `pipeline sessions`, the official checker, and `journalctl -u pipeline` into `evidence/pi4/`. This is the only real power-cut test; the repository's `powercut` scenario is a process-kill simulation.
9. **1-hour resource run on the Pi 4, online, against the deployed cloud:** `sudo /opt/pipeline/bin/measure-resources.sh --duration 3600 --out evidence/resources/pi4-online-1h.json`, then fill the "Pi 4" row of the resource table in docs/DESIGN.md and evidence/SUMMARY.md. The figures currently in the repo come from a Windows/x86 machine and an emulated ARM64 container, which are not Pi 4 numbers.
10. **Record the demo video (≤ 5 minutes):** follow docs/DEMO_SCRIPT.md (network cut, process kill, power cut on the real Pi). Upload it wherever the submission asks.
11. **Review and submit:** read docs/DESIGN.md and README once more, confirm AI_DISCLOSURE.md, and send the repository link (and video link) by email as the assessment instructs.
