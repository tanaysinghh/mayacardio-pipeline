# Failure-test evidence

Generated by `java -jar dist/pipeline-tools.jar summarize evidence` from the JSON files in this directory and in `arm64-ci-history/`. Every run used the **stand-in** mock and checker (not the official tools). Raw logs and databases are not committed.

**A real Raspberry Pi 4 run was not possible** (no board was available). The ARM64 evidence comes from a GitHub Actions native ARM64 runner instead; power cuts are **simulated** by SIGKILL everywhere in this directory, never by removing power.

How to read the columns: *declared* lists losses the device recorded, by reason, in samples; *silent* is samples neither saved nor declared (must be 0). *not verifiable* results are the last window or two whose inputs extend beyond the moment the export was taken. In `mockfaults` the `buffer_overflow` losses come from the injected 15 s mock stall (longer than the mock's 10 s buffer), `sensor_outage` from the injected outages and the unread tail from the injected mock restart. In `diskfull-beyond-buffer` the memory buffer was reduced to 8,000 samples per sensor (20 s) and the disk held full for 45 s, so the oldest ~27 s per sensor were dropped and declared `disk_full`. In `backlog` the stand-in's buffer was set to 200 s of data because data was generated at 20x speed (200 s of data = 10 s of wall time).

## Local amd64 containers

Environment: every failure scenario ran inside a disposable Linux container (`docker/arm64/Dockerfile` built for amd64, JDK 17) on an x86-64 Windows 11 laptop with Docker Desktop: the stand-in mock, the cloud (embedded SQLite) and the device daemon run as separate processes, and the device reaches the cloud through a TCP proxy that black-holes traffic for network cuts. `diskfull-*` fill a 64 MB tmpfs mounted only in that container; `clock` shifts the wall clock of the test's processes with libfaketime (the kernel clock is not touched). `backlog-cloud-0.1cpu` ran the device harness on the host against the real cloud image in a container limited to `--cpus 0.1 --memory 512m` with PostgreSQL 16; `cloud-0.1cpu-startup-and-catchup.json` has its cold-start measurements. Full JSON per scenario (timelines, every check) is in the scenario's `.json` file.

## GitHub Actions native ARM64 runner, live cloud

Environment: **GitHub Actions ubuntu-24.04-arm native ARM64 runner, limited to 4 CPUs / 2 GB; not a Raspberry Pi 4; power cuts simulated by SIGKILL.** Produced by `.github/workflows/arm64-evidence.yml` (`scripts/ci-arm64-evidence.sh`): one container per run (`--cpus 4 --memory 2g --memory-swap 2g`) holds the stand-in mock, the device daemon and the test harness, and the device talks to the deployed cloud over the internet. A network cut disconnects the container from its Docker network (`docker network disconnect`) and a restore reconnects it. `diskfull-*` fill a 64 MB tmpfs mounted only in that container; `clock` shifts the wall clock of the test's processes with libfaketime (the cloud's clock and the kernel clock are not touched); `powercut` is SIGKILL of the daemon and the mock together (the page cache survives, so it is weaker than a real power pull). `soak` is the online resource run: mock started with the exact command `biosignal-mock --mode signal --seed 7 --duration 3600 --port 7100`, daemon started by the production launcher `scripts/pipeline`. Latency here is the cloud's `computed_at` minus this runner's wall-clock time for the window end, so it includes the internet path and the (small) offset between the two NTP-synchronised clocks. The test sessions are deleted from the cloud at the end of the run.

How they relate to a Raspberry Pi 4 (Cortex-A72, 1.5-1.8 GHz, SD card):

- `amd64-native`: x86-64 laptop core, several times faster than a Pi 4 core, so CPU **understates** Pi 4 load; RSS, disk writes and network bytes come from the same code and settings and are close to what a Pi would show.
- `arm64-emulated`: QEMU user-mode emulation on that laptop; binary translation inflates CPU and RSS, so both **overstate** what the same code costs natively on that laptop; the Pi's slower cores push the other way, so this row is not a Pi estimate in either direction.
- `arm64-native-ci`: same instruction set, JVM and settings as the Pi, so RSS, disk writes and network bytes are the most representative; CPU still **understates** Pi 4 load because the runner's server-class cores are much faster than a Cortex-A72 (CPU model in each run's `environment.txt`). Its storage is a cloud disk, not an SD card, so write latency (not volume) differs.
- Bytes written count what reaches the block layer; an SD card's internal write amplification is not visible here. Network bytes depend on the cloud being local (plain HTTP) or remote (TLS).
